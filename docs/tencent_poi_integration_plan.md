# 腾讯位置服务文本地点搜索接入方案

## 1. 文档目的

本文档用于冻结《此地有传说》第一阶段文本地点搜索的 POI 提供商、接入契约和安全边界。

本文档只确定：

- 第一阶段文本地点搜索的服务商
- 未来调用链
- 自有服务接口的输入输出契约
- 结果标准化要求
- API Key 的安全边界

本文档不代表当前项目已经：

- 申请 API Key
- 配置腾讯位置服务
- 发起真实腾讯接口请求
- 创建 CloudBase 云函数
- 实现附近地点搜索
- 实现地理位置授权

---

## 2. 第一阶段服务商冻结

### 2.1 结论

第一阶段文本地点搜索使用腾讯位置服务作为 POI 提供商。

### 2.2 冻结范围

本轮只确定服务商和接口契约，不执行以下动作：

- 不申请 API Key
- 不配置 API Key
- 不发起真实腾讯接口请求
- 不实现附近地点搜索
- 不申请地理位置授权

### 2.3 选择理由

第一阶段选择腾讯位置服务的原因包括：

- 与微信生态适配度高
- 适合作为中文地点关键词搜索的第一阶段候选
- 便于后续通过云函数或后端服务做代理接入

本轮不展开商务、计费、配额或 SLA 比较，仅冻结为第一阶段提供商。

---

## 3. 第一阶段搜索范围

### 3.1 第一阶段只实现

- 用户输入关键词
- 服务端调用腾讯地点关键词搜索
- 返回多个地点结果
- 结果展示名称、地址、城市、省份、类别和经纬度
- 用户选择一个结果后，后续进入现有 `location` 流程

### 3.2 第一阶段不实现

- 附近地点搜索
- 用户当前定位
- 地图展示
- 地图选点
- 路线规划
- 逆地址解析
- 自动扩大搜索半径
- 运行时新增地点落库

### 3.3 当前代码与未来能力的关系

当前 `discovery` 页仍然只支持：

- 系统推荐地点
- 对已加载推荐地点做临时本地筛选

未来接入腾讯位置服务后：

- 推荐地点层仍保留
- 输入关键词进入外部 POI 搜索层
- 搜索结果不再局限于当前 `locations` 集合

---

## 4. 未来调用链

第一阶段文本搜索的调用链冻结为：

小程序 `discovery`  
-> 自有 CloudBase 云函数或后端接口  
-> 腾讯位置服务地点搜索接口  
-> 云函数标准化结果  
-> 小程序展示结果

### 4.1 前端职责

小程序前端只负责：

- 接收关键词输入
- 调用自有服务接口
- 展示搜索中、搜索成功、无结果、失败状态
- 展示多个地点结果
- 接收用户选择某个地点

### 4.2 服务端职责

CloudBase 云函数或后端接口负责：

- 持有腾讯 API Key
- 组装腾讯地点搜索请求
- 过滤、标准化和裁剪返回字段
- 统一输出给小程序

### 4.3 云函数命名

云函数名称可以暂定为 `searchPlaces`，本轮只冻结名称，不创建云函数。

---

## 5. API Key 安全边界

必须严格遵守以下规则：

- 腾讯 API Key 只存在云函数或后端环境变量
- 小程序代码不能出现真实 Key
- 不允许前端直接拼接腾讯接口 URL
- 不允许把 Key 写进 `app.json`、`js`、`wxml`、`wxss` 或测试数据
- 当前阶段不新增任何 API Key

### 5.1 禁止事项

以下做法明确禁止：

- 在小程序前端直接请求腾讯 POI 接口
- 在仓库中硬编码 Key
- 把 Key 写进 CloudBase 测试数据
- 用测试 Key 临时塞进 `project.config.json` 或任意页面脚本

---

## 6. 自有服务接口契约

## 6.1 输入契约

未来自有服务接口的输入冻结为：

```json
{
  "keyword": "南头古城",
  "region": "深圳"
}
```

### 字段说明

- `keyword`
  - 类型：`string`
  - 必填
  - 含义：用户输入的地点关键词
  - 需要 `trim`

- `region`
  - 类型：`string`
  - 可选
  - 含义：用于限定城市或区域，例如“深圳”

### 输入约束

- `keyword` 不能为空字符串
- `keyword` 必须先 `trim`
- `keyword` 长度上限按腾讯地点搜索接口限制为 96 个 UTF-8 字节
- 空关键词不调用外部 POI
- `region` 为可选
- `region` 存在时必须是字符串并 `trim`
- `region` 为空时，第一阶段默认按 `boundary=region(全国,0)` 执行文本搜索
- 第一阶段文本搜索不使用用户当前位置作为前提
- 请求结果最多返回 10 条
- 不把搜索词直接当作 `locationId`
- 当前阶段不传经纬度
- 当前阶段不传附近搜索半径

## 6.2 输出契约

未来自有服务接口返回稳定结构，而列表中的每一个地点结果都必须统一为标准化对象。

单个标准化地点结果对象为：

```json
{
  "provider": "tencent",
  "providerPlaceId": "外部地点ID",
  "name": "地点名称",
  "address": "详细地址",
  "city": "城市",
  "province": "省份",
  "country": "国家或地区",
  "latitude": 0,
  "longitude": 0,
  "category": "地点类别"
}
```

### 输出说明

- `provider` 和 `providerPlaceId` 用于外部地点身份
- `name`、`address`、`city`、`province` 用于展示和辅助去重
- `latitude`、`longitude` 用于地点定位和未来附近搜索
- 第一阶段结果必须返回多个匹配地点，但每条结果都遵守统一的标准化字段契约
- 外部接口原始字段不能直接泄露到页面作为稳定业务契约
- 小程序只依赖标准化后的字段

自有接口成功时整体返回结构冻结为：

```json
{
  "ok": true,
  "results": [
    {
      "provider": "tencent",
      "providerPlaceId": "poi_xxxxx",
      "name": "南头古城",
      "address": "深圳市南山区南头天桥北8米",
      "city": "深圳",
      "province": "广东",
      "country": "中国",
      "latitude": 22.5333,
      "longitude": 113.9294,
      "category": "旅游景点"
    }
  ]
}
```

无结果时返回：

```json
{
  "ok": true,
  "results": []
}
```

失败时返回：

```json
{
  "ok": false,
  "error": {
    "code": "PROVIDER_ERROR",
    "message": "地点搜索服务暂时不可用"
  }
}
```

## 6.3 错误契约

未来接口错误响应至少区分：

- `INVALID_INPUT`
- `CONFIG_ERROR`
- `PROVIDER_ERROR`
- `PROVIDER_TIMEOUT`
- `NORMALIZATION_ERROR`

其中：

- “无搜索结果”不能伪装成服务错误
- “无搜索结果”统一返回 `ok: true` 且 `results: []`
- “服务错误”不能伪装成无结果
- 不向前端返回腾讯 API Key、完整请求 URL 或供应商内部错误细节

---

## 7. 腾讯返回结果标准化要求

未来服务端在把腾讯结果返回给前端之前，至少要标准化为以下字段：

- `provider`
- `providerPlaceId`
- `name`
- `address`
- `city`
- `province`
- `country`
- `category`
- `latitude`
- `longitude`

### 7.1 字段用途

- `provider`：固定供应商标记
- `providerPlaceId`：外部地点稳定身份
- `name / address / city / province`：展示和辅助去重
- `country`：补充展示和跨区域区分
- `category`：展示和分类辅助
- `latitude / longitude`：地点定位和未来附近搜索

### 7.2 第一阶段标准化约束

- `provider` 固定为 `tencent`
- `providerPlaceId` 使用腾讯 POI 的稳定 `id`
- 缺少 `providerPlaceId` 或 `name` 的结果直接丢弃
- 缺少合法经纬度的结果直接丢弃，不伪造坐标
- 腾讯原始返回字段不直接暴露给小程序页面作为稳定契约
- 如果上游返回了结果但标准化后全部失效，应返回稳定的 `NORMALIZATION_ERROR`

### 7.3 页面契约边界

- 小程序页面只能依赖标准化后的字段
- 不允许把腾讯原始字段名直接暴露为前端稳定契约
- 后续如果更换供应商，页面层不应因上游字段名变化而被迫整体重写

### 7.3 第一阶段不做

- 不在第一阶段把搜索结果自动写入 `locations`
- 不在第一阶段自动创建地点详情页数据
- 不在第一阶段自动生成故事

---

## 8. 去重与落库边界

### 8.1 第一阶段边界

第一阶段文本搜索只返回外部地点结果，不自动落库。

### 8.2 后续阶段去重原则

如果未来需要把外部搜索结果转成系统内地点：

1. 优先使用 `provider + providerPlaceId` 判断是否已存在
2. 如已存在现有 `locations`
   - 复用现有 `locations._id`
   - 进入现有 `location` 页面
3. 如不存在
   - 不能只凭 `name` 直接创建
   - 必须先做标准化和重复地点判断
   - 是否自动创建新的 `locations` 作为下一轮单独实现目标

### 8.3 与故事关联的硬约束

- `stories.locationId` 继续指向真实 `locations._id`
- 未落库的外部 POI 不能直接拿 `providerPlaceId` 充当 `stories.locationId`
- 新建地点后，`stories.locationId` 必须使用真实 `locations._id`
- 业务代码不得依赖固定 `_id` 前缀或固定长度

---

## 9. 文本搜索与附近搜索的分离

## 9.1 文本搜索

第一阶段只做文本搜索：

- 用户输入关键词
- 不需要地理位置授权
- 返回多个匹配地点

## 9.2 附近地点搜索

附近地点搜索明确不在第一阶段实现，因为它额外需要：

- 经纬度
- 用户授权
- 地图服务支持
- 附近搜索参数设计

### 冻结结论

文本搜索和附近搜索不是同一个功能，不得合并表述。

---

## 10. 与当前代码的对照关系

当前代码中：

- `discovery` 默认展示 CloudBase `locations` 推荐地点
- 搜索框只是本地筛选 `allLocations`
- 点击结果后继续进入现有 `location` 页

未来接入腾讯位置服务后：

- 推荐地点层继续保留
- 外部关键词搜索层通过自有接口返回多个 POI
- 清空关键词后回到推荐地点层

这意味着：

- 当前本地筛选不会被描述成已完成的全国地点搜索
- 未来腾讯 POI 搜索会作为推荐地点之上的第二层能力接入
