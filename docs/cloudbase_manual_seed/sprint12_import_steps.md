# Sprint 12 手动导入步骤

本说明只对应两类数据：

1. 正式推荐地点 6 个
2. 开发验证地点 1 个

本轮不直接连接远端 CloudBase，也不声称已经完成导入。你需要在 CloudBase 控制台手动执行。

---

## 一、先理解这次为什么是“两步导入”

当前代码要求：

- 正式地点的 `locationId` 必须是真实 `locations._id`
- 民间传说预设故事的 `stories.locationId` 必须回填真实 `_id`
- 模板文件里不能伪造真实 CloudBase `_id`

所以必须按下面顺序执行：

1. 先处理 `locations`
2. 再记录真实 `_id`
3. 再把真实 `_id` 回填到 `stories` 模板
4. 最后再导入 `stories`

## 三、第一步：处理 locations

### 1. 打开 CloudBase 控制台

进入：

- 云开发
- 数据库
- `locations` 集合

### 2. 先按名称检查是否已存在

请逐个检查这 7 个名称：

1. 大鹏所城
2. 赤湾天后宫
3. 惠州西湖
4. 十里银滩
5. 陈家祠
6. 西湖断桥
7. 开发验证点·民间传说回退

### 3. 判断规则

- 已存在：不要重复创建，不要覆盖原有 `_id`
- 不存在：才导入 `locations.sprint12.manual.csv` 或 `locations.sprint12.manual.jsonl`

推荐顺序：

1. 如果你只需要快速导入，优先用 `csv`
2. 如果你希望保留 `tags` 数组结构，优先用 `jsonl`

关于 `tags` 再补充一句：

- `locations.tags` 的最终目标类型是数组
- `JSONL` 导入时可以直接保留数组
- `CSV` 导入时，CloudBase 可能会把 `tags` 保存成字符串
- 当前代码已经兼容历史字符串 `tags`，所以不用因为这个问题删地点或重导故事
- 但如果是新一轮导入，仍然更建议优先使用 `JSONL`

### 4. 导入完成后，记录真实 `_id`

导入完成后，请回到 `locations` 集合列表页，逐条查看刚才这 7 个地点。

你需要记录每个地点的真实 `_id`。

### 5. 在哪里查看和复制 `_id`

5. 复制 `_id` 的真实值

## 四、第二步：回填 stories 模板并导入

### 1. 只给 6 个正式推荐地点填故事

本轮故事模板文件只有这两个：

- `stories.sprint12.manual.template.csv`
- `stories.sprint12.manual.template.jsonl`

它们都只包含 6 条正式地点的民间传说预设故事。

### 2. 回填方式

模板里的 `locationId` 现在统一写成：

`<填写真实 locations._id>`

在导入前，你必须把每一行的这个占位值替换成对应地点的真实 `_id`。

对应关系如下：

| 故事标题 | 应绑定地点 |
| --- | --- |
| 海风替城门守夜 | 大鹏所城 |
| 潮声里的护航祈愿 | 赤湾天后宫 |
| 湖面会替人藏起一句心事 | 惠州西湖 |
| 被海浪带回来的名字 | 十里银滩 |
| 木雕会记住来过的人 | 陈家祠 |
| 桥未断，故事先被雪藏起来 | 西湖断桥 |

### 3. 严格检查

在点击导入 `stories` 前，请确认：

- 每一条 `locationId` 都已经替换成真实 `_id`
- 没有任何一条还保留 `<填写真实 locations._id>`
- 没有把不同地点的故事填成同一个 `locationId`
- 没有给“开发验证点·民间传说回退”新增任何 `folk` 预设故事
- 所有故事都保持：
  - `type = folk`
  - `status = published`
  - `source = folk_archive`

### 4. 导入后如何检查

导入完成后，请到 `stories` 集合里逐条确认。

建议至少检查以下查询条件：

- `locationId = 真实地点 _id`
- `type = folk`
- `status = published`

你需要能确认每个正式推荐地点至少有 1 条符合条件的记录。

## 五、开发验证点的单独要求

“开发验证点·民间传说回退”必须满足：

- 在 `locations` 中存在
- `status = published`
- `discovery` 可以加载并搜索到
- 不存在任何：
  - `locationId = 该点真实 _id`
  - `type = folk`
  - `status = published`

这样它才能用于验证：

1. 进入测试点
2. 点击“民间传说”
3. 先查 folk 预设
4. 查询为空
5. 回退调用 DeepSeek

## 六、幂等与人工安全检查

当前 CloudBase 控制台不适合做真正的安全 upsert。

所以这次要靠人工检查来保证幂等：

### locations

再次执行前，先检查名称是否已存在：

- 已存在就复用，不重复导入
- 不存在才导入

### stories

再次执行前，先按以下组合检查是否已有等价预设故事：

- `locationId`
- `type = folk`
- `title`

如果已经有等价故事：

- 不要重复导入
- 如需更新内容，请人工编辑已有记录

### 明确不做的事

- 不删除已有地点
- 不覆盖已有 `_id`
- 不删除已有故事
- 不修改南头古城已有故事
- 不因为 `tags` 类型问题重复创建地点
- 不因为 `tags` 类型问题重复导入 stories

## 七、这轮建议你实际操作的顺序

1. 打开 `locations` 集合
2. 逐个搜索 7 个地点名称
3. 记录哪些已存在，哪些不存在
4. 只导入不存在的地点
5. 导入后逐条复制真实 `_id`
6. 打开 `stories.sprint12.manual.template.csv` 或 `.jsonl`
7. 把 6 条正式故事的 `locationId` 全部回填成真实值
8. 再导入 `stories`
9. 回到 `stories` 集合按 `locationId + type=folk + status=published` 检查
10. 单独确认测试点没有任何 folk 预设故事
