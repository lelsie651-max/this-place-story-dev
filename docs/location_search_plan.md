# 地点搜索方案冻结

## 1. 文档目的

本文档用于冻结《此地有传说》地点入口的产品方案、数据契约和架构边界。

本文档只描述：

- 当前已实现的推荐地点与临时本地筛选
- 已确认但尚未实现的外部 POI 关键词搜索
- 未来地点身份、去重、标准化和安全边界

本文档不代表当前代码已经接入外部地图或 POI 服务。

---

## 2. 当前实现与最终目标

### 2.1 当前已实现

当前 `discovery` 页已经实现两层能力中的第一层和一个临时过渡能力：

1. 默认展示系统推荐地点
2. 对当前已加载的推荐地点做本地关键词筛选

当前代码的真实来源：

- 推荐地点来自 CloudBase `locations` 集合
- 查询条件为 `status = "published"`
- 页面加载时读取最近已发布地点
- 搜索框只对页面内存中的 `allLocations` 做本地筛选

### 2.2 当前实现的准确定位

当前本地筛选只是临时阶段能力，不能称为：

- 全国地点搜索
- 地图搜索
- POI 搜索
- 外部地点搜索

当前本地筛选的作用仅是帮助用户在“已经加载到页面的推荐地点”里更快定位目标地点。

### 2.3 最终目标

最终产品希望采用类似微信位置的两层地点入口：

1. 页面默认显示系统推荐地点
2. 用户输入关键词后，搜索推荐列表之外的真实地点
3. 搜索结果来自外部 POI / 地点服务
4. 搜索结果可以返回多个匹配地点
5. 用户选择一个地点后，继续进入现有 `location` 页面

---

## 3. 两种地点来源

## 3.1 A. 系统推荐地点

### 当前阶段来源

- CloudBase `locations` 集合
- 当前已发布的 `locations`
- 页面进入时默认展示
- 搜索框为空时恢复展示
- 这些地点可以是人工维护的推荐地点

### 在最终产品中的地位

这一层在最终产品中仍然保留，用于：

- 提供默认入口
- 承接运营推荐
- 提供稳定可探索的地点池

### 当前与未来共同约束

- 推荐地点必须是系统认可的可展示地点
- 推荐地点进入 `location` 页时仍然使用真实 `locations._id`
- 推荐地点不能和外部搜索结果混为同一种数据来源描述

---

## 3.2 B. 外部地点搜索结果

### 未来来源

- 外部地图或 POI 服务
- 用户输入关键词后查询
- 结果不局限于当前 `locations` 集合
- 可以返回当前系统尚未预存的地点
- 可以返回多个匹配地点

### 结果展示要求

搜索结果至少应展示足以区分地点的信息，例如：

- 名称
- 地址
- 城市
- 省份
- 类别或补充说明

### 冻结结论

- 当前 `91bf8ec` 的本地筛选只是临时能力
- 当前本地筛选不能称为全国地点搜索
- 接入 POI 后，最终搜索关键词不应只筛选 `allLocations`
- 清空关键词时仍然回到系统推荐地点列表

---

## 4. 最终页面状态

地点页入口的最终状态机冻结如下：

### 4.1 初始状态

- 显示系统推荐地点
- 不显示外部搜索结果

### 4.2 用户输入关键词

- 进入外部地点搜索状态
- 不再只依赖当前内存中的推荐地点

### 4.3 正在搜索

- 显示“地点搜索中”的独立状态
- 不把“正在搜索”伪装成“没有结果”

### 4.4 搜索成功

- 显示多个 POI 结果
- 每条结果带足够的区分信息

### 4.5 搜索无结果

- 显示“没有找到相关地点”
- 明确这是搜索无结果，不是系统故障

### 4.6 搜索失败

- 显示“搜索服务暂时不可用”
- 不伪装成“没有结果”
- 不把错误结果混入推荐地点列表

### 4.7 清空关键词

- 返回系统推荐地点
- 不把搜索结果混入推荐列表

## 5. 地点身份和去重规则

### 5.1 外部地点身份

外部 POI 的 `providerPlaceId` 是外部地点身份的首选依据。

冻结规则：

1. 同一个外部 POI 多次搜索不能生成多个 `locations` 记录
2. 如果搜索结果已经对应现有 `locations`
   - 复用现有 `locations._id`
   - 不新建重复地点
3. 如果搜索结果尚未存在
   - 必须先经过地点标准化和去重判断
   - 再决定是否创建新的 `locations` 记录

### 5.2 当前代码保持不变的规则

- 业务代码不得依赖固定 `_id` 前缀或固定长度
- `stories.locationId` 必须继续指向真实 `locations._id`

### 5.3 标准化判断建议

未来做外部地点落库前，至少应比较：

- `provider`
- `providerPlaceId`
- `name`
- `address`
- `city`
- `province`
- `country`
- `latitude`
- `longitude`

如果缺少 `providerPlaceId`，不得直接用名称字符串当作唯一身份。

## 7. 未来搜索架构边界

### 7.1 安全边界

冻结规则如下：

- 外部地图服务 API Key 不得写入小程序前端
- 未来应通过 CloudBase 云函数、后端接口或等价服务代理请求
- 小程序只调用自己的服务接口
- 当前阶段不新增任何 API Key
- 当前阶段不接入任何地图服务

### 7.2 前后端职责

前端小程序负责：

- 展示推荐地点
- 接收关键词输入
- 展示搜索状态、结果、错误和无结果
- 接收用户选择的地点

服务端或云函数负责：

- 调用外部 POI 服务
- 管理 API Key
- 进行结果标准化
- 进行地点去重判断
- 决定是否复用现有 `locations`
- 决定是否创建新地点

## 8. 文本搜索与附近搜索

这两类能力必须明确拆分，不能写成同一个功能。

## 8.1 文本搜索

定义：

- 用户输入关键词后，对外部地点服务发起文本查询

特点：

- 不需要地理位置授权
- 返回与关键词相关的多个地点结果
- 适合搜索明确地名、景点名、商圈名等

当前状态：

- 尚未实现
- 当前只有“对已加载推荐地点的本地筛选”

## 8.2 附近地点搜索

定义：

- 基于用户当前经纬度，搜索附近地点

特点：

- 需要经纬度
- 需要用户授权
- 需要地图服务支持
- 需要处理定位失败、授权拒绝和精度问题

当前状态：

- 当前暂不实现
- 不应与文本搜索合并描述

---

## 9. 与当前代码的关系

### 9.1 当前推荐地点链路

当前代码中的推荐地点链路是：

首页
-> `discovery`
-> CloudBase `locations`
-> `location`

### 9.2 当前本地筛选的定位

当前 `discovery` 页里的搜索框：

- 只筛选当前已经加载的 `allLocations`
- 不会创建新地点
- 不会改变 `locations._id`
- 点击结果后仍进入原有 `location` 页面

它在最终产品中的定位是：

- 临时过渡能力
- 方便用户在推荐地点里快速定位
- 不是最终的地点搜索能力

---

## 10. 暂不实现清单

以下能力本轮仅冻结方案，不进入实现：

- 外部 POI API 接入
- 地图服务 API Key 配置
- 云函数或后端代理接口
- 未预存地点的自动落库
- 地点标准化流水线
- POI 去重与地点合并
- 附近地点搜索
- 地理位置授权
- POI 供应商最终选型
